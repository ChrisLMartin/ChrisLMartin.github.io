Checking BGP when the VPN tunnel is up

How to distinguish healthy tunnels, missing routes and reduced redundancy during a VPN incident.

In a routing incident I helped investigate, IPsec tunnels stayed connected while some Border Gateway Protocol (BGP) sessions failed to re-establish. The tunnel status missed the routing problem. I now split the checks into tunnel state, peer state, route coverage and actual traffic.

Check peers and prefixes

Start with the state of each expected peer. Then compare what each side advertises with what the other side has learned. An established session can still be missing the prefix a workload needs.

Keep a known-good snapshot and make two comparisons:

  • Compare prefixes. If an expected prefix disappears, check the effective route to the destination. Another route may still cover it, or traffic may have lost its expected path.
  • Compare prefixes and next hops together. If the prefix remains but a next hop disappears, traffic may still flow with less redundancy. That needs a different alert and response from a complete loss of the destination.

Check that traffic works again

Once the expected peers and routes return, test an application-level connection from a representative source. Include the return path in the investigation because a route in one direction only tells half the story.

For monitoring, start with per-peer BGP state and add checks for the prefixes that matter to workloads. Keep a separate signal for reduced redundancy if failover matters. Those signals let an on-call engineer tell whether to restore service immediately or investigate a degraded backup path.
