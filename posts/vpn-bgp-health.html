Checking BGP when the VPN tunnel is up

In a routing incident I helped investigate, the IPsec tunnels stayed connected while some Border Gateway Protocol (BGP) sessions failed to re-establish. Tunnel status alone missed the failure.

Check the tunnel, peer and routes

Check the BGP state for each expected peer, then compare learned and advertised routes with what you expect on both sides. An established BGP session can still be missing the prefix the application needs.

Save a known-good snapshot for comparison. I find it useful to answer two questions separately.

  • Are the expected prefixes still present? Compare the set of learned prefixes with the baseline. If an expected prefix is missing, check whether traffic to that destination still has a usable route.
  • Did we lose a path? Compare prefixes together with their next hops. Losing one next hop while the prefix remains can indicate reduced redundancy, even if traffic still flows.

Verify recovery from both sides

Check that the expected peers and routes return, then test traffic from a representative source to its destination and check the return path. That gives you evidence of both routing recovery and usable connectivity.

For monitoring, use tunnel status alongside per-peer BGP metrics and checks for critical prefixes. Keep the distinction in the incident review so a future responder knows whether an alert points to lost connectivity or a degraded failover path.
