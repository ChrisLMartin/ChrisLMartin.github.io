Keeping human approval in AI-assisted PR review

How to make automated review output useful while keeping the approval attached to a person and a revision.

When I looked through repeated DevOps tasks, pull request review and build triage were natural candidates for reusable workflows. The useful automation prepared evidence and surfaced issues. A person still made the approval decision.

Tie a review to a revision

Start from the current diff and PR context, then record the exact revision reviewed. A clean review can queue the PR for a person. A new revision removes the queued result and requires a fresh review before it is eligible again. Otherwise an approval decision can accidentally rely on an older diff.

Make the queue easy to act on

The queue includes a short summary and points to unresolved threads so the reviewer knows where to start. If the author pushes another revision, a human votes or the PR stops being active, it drops out of the queue. The developer still has the normal review controls and can inspect every finding.

The automated reviewer also treats threads as belonging to their authors. It can suggest that a thread is resolved, while leaving someone else’s decision to close their discussion with them.

Exercise the state transitions before enabling writes

Use dry runs and intercepted writes to test a clean review, a new revision after review, existing human feedback and a PR that returns to draft. I found this more useful than tuning the reviewer on one happy-path diff. The state transitions determine whether the workflow stays trustworthy once people start using it.
