Staging Azure Policy enforcement with a CI guard

How to turn a staged rollout convention into a check that runs before deployment.

When a new Azure Policy assignment can deny a request or change a resource, the rollout deserves its own review. We wanted teams to start new assignments in DoNotEnforce, inspect the results, and then enable enforcement in a deliberate follow-up. I added a CI check so that convention was checked as part of every plan.

Validate the effective configuration

Check the policy’s effective behaviour. A plan may omit a parameter when the assignment takes its default, so reading only the assignment parameters can miss the effect entirely. Look at the definition and resolved parameters, including initiatives that group several policies.

Separate a new assignment from an intentional transition to enforcement. The first should normally start with enforcement off. A reviewed follow-up can then turn it on. Treat missing information explicitly so reviewers can see which decisions the automation could resolve.

Test both sides of the rollout

  • A new assignment that starts unenforced passes.
  • A new assignment that starts enforced is flagged before deployment.
  • A follow-up that enables an existing staged assignment follows the enforcement review path.

The guard later stopped a plan that would have recreated enforcing assignments after live state had drifted. That was worth investigating even though the assignment definitions themselves had not changed. We reconciled the live state and reran the plan.

Keep the review visible

Run the check in pull requests and again before deployment. Have it explain which assignment was flagged and which effective policy behaviour triggered the check. Reviewers can then inspect the same evidence before deciding how to move forward.
