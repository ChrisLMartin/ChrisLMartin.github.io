Fixing intermittent Bicep lint failures without slowing every build

A way to measure the cost of a flaky lint step and keep real compilation failures visible.

A shared CI task linted Bicep files in parallel. An occasional run failed with a module restore diagnostic, even when other files using the same artifact built successfully. Serialising every restore was a plausible fix. Before making it permanent, I wanted to know what it would cost.

Compare the cost of the fix with the failure

I counted the matching failures in pipeline history, then measured the added time from a serial restore. The serial approach penalised every affected run, including clean ones. Across the observed workload, that extra agent time exceeded the time lost to the failures. The measurements ruled out the workarounds that looked simplest in a single build.

Retry the smallest useful unit

The revised approach kept the first pass parallel. After it finished, the task re-linted only files that reported the restore diagnostic associated with the race. A successful retry replaced that file’s earlier result. If the diagnostic persisted, or the file had another compilation error, the run still failed. A known missing artifact was part of the test so the retry could not silently convert a broken build into a pass.

Test the failure path as well as the clean path

I checked three cases: a clean pass that performs no extra work, a simulated restore race that the follow-up lint can clear, and a genuinely missing artifact that still fails. A live CI run confirmed the revised task worked with the normal pipeline. Those cases are also a useful regression test when the linter or module restore behaviour changes.

For any flaky CI step, start with the frequency and cost of the failure. Then test the smallest recovery you can express without losing the compiler’s signal.
