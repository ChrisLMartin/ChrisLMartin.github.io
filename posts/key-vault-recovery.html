Recovering a Key Vault and restoring service

What to verify after soft-delete recovery, from restoring permissions to testing a workload read.

During a Key Vault recovery I helped with, the vault and its contents came back before the applications could use them. The recovery had two milestones. First we recovered the resource. Then we restored and verified the service that depended on it.

Rebuild the access the workload needs

Recovering a soft-deleted vault can bring back its keys, secrets and certificates within the retention window. Integrations such as vault-scoped Azure RBAC assignments and Event Grid subscriptions need to be recreated separately.

Use the desired configuration as your starting point. If it’s incomplete, Activity Log history can help establish which role assignments existed before deletion. Compare the expected principals, roles and scopes with what is live now. Avoid using a broad grant as a shortcut when the previous access can be recovered precisely.

I prepared a script that previewed the proposed changes, applied only the agreed assignments and skipped any that already existed. Previewing the diff gave someone else a chance to check it. Skipping existing assignments meant we could rerun after a partial failure.

Verify access from the application’s side

Exercise a representative operation using the workload’s identity and usual network path. An administrator reading the same secret from a different network tests a different access path. Use diagnostic logs to confirm that the workload identity made a successful call, and verify other integrations separately if the service depends on them.

If a network dependency appears to be missing, compare with a known-good configuration or earlier telemetry before rebuilding it. Record what was restored, how the application was checked and anything that remains unresolved. That gives the next responder a usable recovery procedure.
