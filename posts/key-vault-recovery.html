Incident lessons · Azure Key Vault

Recovering a Key Vault and restoring service

A vault can reappear in Azure before applications can read from it. I helped with a recovery where restoring access was a separate step.

Rebuild the access the workload needs

Azure Key Vault soft-delete can recover a vault and its contents within the retention window. Azure role assignments scoped to the vault and integrations such as Event Grid subscriptions may have to be recreated.

In this recovery, we used Azure Activity Log history to help identify deleted role assignments. I prepared a script that previewed the proposed changes, applied only the agreed vault-scoped assignments and skipped assignments already present. That made the plan reviewable and gave us a safe way to rerun it.

Verify access as the application

A successful read by an administrator tells you little about the application's identity or network path. Exercise a representative operation using the workload identity from its usual network, then look for a successful call from that identity in Key Vault diagnostic logs. Verify any event subscriptions or other integrations the workload depends on separately.

If a networking dependency appears to be missing, compare with a known-good configuration or earlier telemetry before rebuilding it. That distinction helps avoid adding a dependency the workload never used.

Make the recovery repeatable

Keep the expected permissions and integrations under version control where possible. Document the verification steps alongside the restore steps so the next person can confirm recovery from the workload's perspective.
